# Consult: owner experience and adoption

Lens: a 45-year-old Pilates studio owner who took one online Claude Code class. Reviewed 2026-10-14 against the tree as it stands (executor, arbox-api SKILL.md and arbox-recipes not yet written; briefs in .team/tasks/B04.md and B06.md).

Headline: the design is thoughtful and safe, but the owner's path to a first report is long, and every step between "install" and "report" is a place a non-technical person quits. The biggest risks are not safety. They are (1) a dead README and a probably-wrong install line, (2) five interview rounds before any value, (3) the key hunt, which may dead-end on a plan or support gate, and (4) a terminal full of permission prompts the skills never prepare her for.

## 2. Decisions I would challenge

- **D13 (HTML + CSV only; no scheduling).** Accept for v1 but the owner promise "rerun by one sentence" needs Claude Code open. She will not remember. The real retention loop is "Monday I open Claude and it is already there". Cheap partial fix: the routine file (recipes-decision.md "Monday page") must print its own one-line re-run phrase at the end of each report. Do not promise scheduling.
- **D2/D4 plus the interview shape.** Interview-before-value is the design's core bet (owner-journey.md:16, 29-33). I would flip it: one question, show a result. For a looks-only, read-only quick win, the right order is: pitch (3 lines) -> "Which hurts more, empty classes or people quitting?" (1 question) -> connect -> first report -> THEN profile interview as part of "make it better". Rounds 1-4 collapse to 3 questions. The returning-owner branch already skips most; make that the default.
- **D6 (key via a file the owner edits).** Principled and correct, but the executor is the one with the "paste into a text file" step that is the second most likely failure. Add the executor-level interactive path: `arbox setup` asks "Paste your key and press Enter" using `read -s` (no echo, never goes through chat or argv) and writes the file itself. In Claude Code the owner can run it with the `!` prefix, which is exactly the "LIVE CHECK: does `!` accept hidden input" already listed (owner-journey.md:300, 323). If `!` works, TextEdit is the fallback, not the main path. Test this first; it removes smart quotes, RTF, hidden-folder and wrong-line failures at once.
- **D7 tiering is safe, but "R1 needs in-chat confirmation" and the permission prompt are two different gates for the owner.** She cannot tell them apart. Say in the SKILL: "You'll see a grey box asking permission. For reading, say yes always. For anything that changes Arbox I will ask in my own words first, then you'll see the box again."
- **D10 (branch on operating model and plan tier).** Plan tier is a question she cannot answer (interview.md:38). Never ask; detect it by whether leads/auto-action endpoints respond after connect. Drop 2.1.
- **D12 privacy notice "in setup".** Fine, but make it one sentence and not a gate. A legal-sounding notice before she has seen value costs trust. Show it once at connect, with the real column list ("we skip health, injury, salary").
- **D14 (two channels).** Right for developers. For owners the plugin channel is the only one that matters. The README must lead with a 3-step plugin install and relegate `npx` to a footer.
- **Recipe choice (9 recipes plus Monday page).** The justification "Recipes are on-demand reference files, so only the index costs context" (recipes-decision.md:19) is right on cost, wrong on risk. Every recipe is another unverified assumption about field shapes (L7). For TODAY, ship the 3 that are strongest and most checkable and mark the other six "beta: may need adjusting". Which three: **Renewal watch** (pack/membership expiry; typed fields, the owner knows the answer), **Who's drifting** (best "wow", but gated on `last_seen` semantics; ship only with its caveat visible on the page), **Payments to chase** (she cares about money first, typed `debt` field). Revenue snapshot is next. No-shows, first-30-days and waivers are real but each adds a failure surface for a day-one release.

## 3. What is missing for day one

1. **A demo mode with no key.** The biggest unlock for adoption. Ship a fake studio ("Studio Flow", 40 members, Hebrew and English names) as a bundled JSON and let `arbox read` serve it when the owner says "show me with sample data" (or when there is no key at all). The guide's step 7 then ends with an actual report she can look at, in 2 minutes, before she touches Arbox or finds a key. The report template can already be built against this data (B06 needs sample rows anyway). This also helps the key-hunt dead end: she can see the value while waiting for Arbox support. It is also the cheapest way to test the HTML template.
2. **A guided first-run command / slash command.** A single `/arbox` (plugin command) that starts the pitch, so she does not depend on trigger-word luck. Plugins can ship commands; this removes the "wrong skill fires" risk for the first message. One file.
3. **"I cannot find my key" path.** A paste-ready email to Arbox support ("Hi, please enable API access and send my API key for <business>. Which plan includes it?") in both Hebrew and English, in `arbox-api` setup. Plus "I will keep the plan; ping me when you have it" via the profile file (`Connected: waiting for key`). questions-for-arbox.md already has the questions; give the owner the short version.
4. **A one-page printable cheat sheet** (HTML in `arbox-guide/assets`): "Things to say to Claude: Who's drifting? Who owes me? Run my Monday page. What did you just do?" plus "How to open the report folder". She will forget the routine names. Include the folder shortcut: tell her `open ~/Arbox/reports`.
5. **"What did Claude just do" log.** Already half-designed: `~/Arbox/logs/actions.log` records writes. Reads are not logged. For trust, a plain-English `activity.md` of the last N actions ("Read your members list (183 rows) at 10:14; wrote drifting-members.html") would answer her unspoken fear. One line per executor call, no payloads. The ticket 02 executor can do this in a few lines. Surface it in the guide: "Want to see everything I did? Say 'show my activity'."
6. **Report opens reliably.** Say "I'll open it in your browser" and verify with `open file://...`. Provide the full path in chat. Many owners will not know where `~/Arbox` is: tell her once: "Finder > Go > Home > Arbox".
7. **Error vocabulary in owner words.** The executor's messages (arbox:208 etc.) are good ("Arbox rejected the key"). Check that the SKILL tells the agent to relay them in her language and not to paste curl output.
8. **Windows.** Many Israeli studio owners use Windows. The executor is POSIX `sh`; Claude Code on Windows works through Git Bash, but TextEdit/`open -e` do not exist. State "Mac first; Windows: ask me" in the README, or the Windows owner gets a stack trace. At minimum the README says it.
9. **The Hebrew first run.** Eval 4 exists. The reports must be RTL-correct (template uses `dir="auto"`). Also the plugin description and README are English-only; a Hebrew owner searching GitHub finds nothing. A 5-line Hebrew section in the README is nearly free.

## 4. What to cut to ship today

- **Interview rounds 2 and 4 as rounds.** Keep 6-7 questions in total; the question bank can stay as a reference (it is a reference file, no cost), but SKILL.md:37 must say "max 2 rounds before the first idea".
- **The plan-tier question (interview.md:38) and the no-show-fee question (41).** Unanswerable for her; detect or skip.
- **Three of nine recipes at launch**: no-shows, first-30-days, waivers-and-forms. Keep the files if written, but do not list them in the guide's hand-off line (skills/arbox-guide/SKILL.md:108) or the plugin description (.claude-plugin/plugin.json:4) until verified live. Marketing a recipe you could not test is the fastest way to a public bug report.
- **R2 booking/cancellation by the agent** (B04 lead addendum). One person at a time, with confirm. For day one an owner who types "cancel Dana's class" is the highest-regret mistake available. The cost of dropping it is near zero for the audience. Treat all of R2 as drafts-only/refused today; add it back when the test gym has run it.
- **Multi-profile / multi-location UX in the owner path.** Keep the executor feature; do not mention it in the pitch.
- **The "Think beyond Arbox data" table (SKILL.md:86-101)** is useful but long. Keep three rows (posts, WhatsApp templates, class descriptions). It is read on every guide invocation.

## 5. Top 5 recommendations (impact / effort)

1. **Fix the front door: README + the install line.**
   File: `README.md` (replace lines 5-15). Content: one sentence of what it does; a screenshot or a text mock of the "who's drifting" report; the exact two plugin commands (verified in ticket 07 smoke), then "open Claude Code and type: I own a Pilates studio on Arbox, what can I do?"; Mac first, Windows "ask"; community-not-affiliated; a short Hebrew paragraph. Also fix `skills/arbox-guide/SKILL.md:111` to the verified two-step syntax. Effort: 30 min. Impact: without it nobody gets in.

2. **Cut the interview to a short path with a result.**
   File: `skills/arbox-guide/SKILL.md` lines 35-48 and `references/interview.md` lines 5-12, 38-41. Change: "max two rounds (type + size + top pain + 'look only or drafts?') before proposing; plan tier and no-show fee are never asked; everything else is learned after the first report". Effort: 20 min. Impact: removes the largest boredom drop-off.

3. **Make key entry foolproof; add a no-key path.**
   Files: `skills/arbox-api/scripts/arbox` (`setup`: prompt with hidden input when a TTY is available, strip quotes/whitespace/smart quotes when reading the key, reject RTF, fall back to `open -e` otherwise) and `.team/tasks/B04.md` -> `skills/arbox-api/references/setup.md` (paste-ready support email in HE/EN; "no key yet: keep going with sample data"). Test `!` hidden input now (L6). Effort: 1-2 h. Impact: this is the likeliest hard stop in the whole journey.

4. **Sample/demo data so the first report needs no key.**
   Files: `skills/arbox-recipes/assets/sample/*.json` plus a note in the future `skills/arbox-recipes/SKILL.md` ("if no key and the owner wants to see an example, run the recipe against the sample files and label the report SAMPLE DATA in the header"). The template needs sample rows for B06's headless render check anyway. Effort: 1 h. Impact: she sees a real report in minute 12 and has a reason to push through the key hunt.

5. **Prepare her for permission prompts and show the activity log.**
   Files: `skills/arbox-api/SKILL.md` (a "before the first command, tell the owner what grey boxes to expect, and which answer is safe: yes to reads, read me before you say yes to anything else") and the executor (append a one-line plain English entry per `read` and `write` to `~/Arbox/logs/activity.log`; ticket 02 already logs writes at `docs/plan/tickets.md:74`). Add "show my activity" to the guide's cheat sheet. Effort: 45 min. Impact: protects the safety model from her own click-through habit, and answers "what did it just do?".

Honorable mention (do if time): ship only 3 verified recipes in the plugin description and guide hand-off list (`.claude-plugin/plugin.json:4`, `skills/arbox-guide/SKILL.md:108`), and drop agent-initiated R2 bookings for v1.

## What I did not find fault with

D5 (sh + curl), D6 (key never in chat), D7 (R3 never), D9 (docs links), D11 (mirror language), D15. The audit trail and the honest "Arbox already does this" stance (SKILL.md:101) are the strongest trust builders in the design. Sample transcript (owner-journey.md:49-95) is excellent; the real thing just needs to be shorter.
